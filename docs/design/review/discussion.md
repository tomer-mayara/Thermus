# Review discussion and agreed direction

This record describes an actual exchange between two AI reviewers using Martin-informed and Metz-informed perspectives. Robert C. Martin and Sandi Metz did not participate and have not endorsed the result. The review concerns repository baseline `68a8eda`, dated 2026-10-11. It authorizes no implementation.

The reviewers first wrote independent [Martin](martin-proposal.md) and [Metz](metz-proposal.md) proposals. Each then read the other proposal and wrote a reciprocal review: [Martin review of Metz](martin-review-of-metz.md) and [Metz review of Martin](metz-review-of-martin.md). They sent direct messages to resolve concrete differences. The [unified principles](../oo-principles.md) and [engineering plan](../oo-refactoring-plan.md) supersede the independent drafts as the agreed direction. The manager reviewed both proposals, reciprocal reviews, and final documents, and signed off this documentation handoff on 2026-10-11. Verification covered seven Markdown documents, 68 local links, and four explicit test-command paths. This sign-off covers the documents; implementation and runtime checks remain unstarted.

## Evidence and common ground

The review used production code for ad-engine ownership, parser source mapping, hidden-HTML scanning, removal-pass coordination, CSS cascade, prepared-document conversion, and fetch request lifetime. Existing malformed-tree and removal-pass tests, sanitizer and processing-limit documents, package scripts, and [AGENTS.md](../../../AGENTS.md) supplied behavior and process constraints. No implementation was changed and no tests were run for these documents.

The reviewers agreed that source mapping, removal sessions, and extraction coordination have concrete ownership problems. They also agreed to preserve existing objects, pure calculations, useful closures, parser distinctions, and boundary data records. The Martin perspective made the class preference explicit for domain roles and protected state. The Metz perspective required that each boundary reduce the knowledge a client must carry. The unified principles retain both positions: a meaningful role may be stateless, and a class does not require a second implementation, but its benefit must be stated.

## Actual objections and concessions

The Martin draft proposed immediate `CssVisibilityCascade` extraction. The Metz reviewer objected because `RuleContext` is private to a small resolver with one local client. No external caller currently coordinates its mutable state. The Martin reviewer conceded that the current gain did not justify immediate conversion. The accepted decision defers the class until multiple clients, separately invoked operations, or an externally coordinated lifecycle make the boundary useful. Module growth alone is not sufficient evidence.

The Metz draft proposed an extraction callback accepted by `PreparedHtmlDocument`. The Martin reviewer objected that it creates an unused extension point while preparation already contains concrete Defuddle knowledge. The Metz reviewer conceded direct dependency ownership. Both accepted `PreparedHtmlDocument.extract(sanitizeText): Promise<{ content, title }>`: the object owns preparation, marker lifetime, the concrete Defuddle call, and postprocessing. Both sanitation stages remain observable. During final document review, the manager identified that passing `sanitizeText` to both preparation and extraction left the caller responsible for supplying the same callback state twice. The refined API is `PreparedHtmlDocument.fromHtml(html, url)`, which parses and captures fragment status, followed by `extract(sanitizeText)`, which owns normalization, source sanitation, preserved-content decisions, preparation, local extraction setup, Defuddle sanitation, and finishing. The sanitizer is supplied once. This preserves the current order and strengthens ownership. Migrate the one production caller atomically; the old record factory is not a drop-in forwarding wrapper. The Martin reviewer conceded the `PreparedHtmlDocument` name instead of `HtmlExtractionSession`. No generic extractor framework was agreed.

The source-query proposals differed in policy wording. Metz's `visibleStyleSources` implied a visibility decision; Martin's `elementRemovalRanges` implied deletion policy. Both accepted neutral queries: `SourceHtmlDocument.parse`, `sourceElement`, `textRanges`, `styleSources`, and `elementTagRanges`. The source object combines source facts; the scanner decides visibility and deletion. Private adopted-source and decoded-style maps no longer form the proposed client contract.

## Verification corrections

The Martin draft required the whole interface command. The manager identified that it includes live public renderer tests, which need not gate unrelated source-only changes. The Martin reviewer corrected this to affected local dependency-interface suites. The Metz draft also included new concurrent fetch isolation scenarios in initial acceptance work. Both reviewers retracted that scope: new fetch concurrency tests belong to future fetcher work. Concurrent reuse of one sanitizer remains relevant because the removal-session lifetime changes.

The manager corrected the Metz draft's claim that real pipeline stages alone establish integration tests. AGENTS defines integration through actual Delamain package boundaries. Real collaboration inside one package is allowed in unit tests. The unified documents classify tests by those boundaries and their purpose, with no test relocation in this refactor.

The final accepted order is the ad-cleaner instance method, encapsulated source queries, per-invocation `HiddenHtmlRemovalSession`, and prepared extraction ownership. CSS cascade, fetch lifecycle, and dependency mathematical objects remain deferred. BDD/TDD, passing characterization coverage, DRY3, current repository gates, counters, failure contracts, and source preservation remain constraints. Resolve the missing referenced test-gate policy at implementation handoff. No peer disagreement remained when the manager requested synthesis.
