# FS-01: free hosted activation

Signup stays disabled. This change publishes no policy page, supplies no
production legal bundle, and changes no production WorkOS or Render setting.

## Behavior

`SELF_SERVE_SIGNUP_ENABLED` accepts exactly `true` or `false`. Omitted means
false; an invalid value stops startup. The server reads it at startup, so a
change needs a restart. When disabled, `/signup` shows a closed notice with
Sign in and Contact links. An old form gets HTTP 403. Neither route reads a
session or calls WorkOS. HEAD has no body and makes no provider call. Contact
uses `legal@thermus.ai`, the address in the approved defaults and marketing source.

When enabled, the route requires an approved document bundle at composition.
It validates and freezes the exact UTF-8 terms and privacy-notice bytes,
SHA-256 hashes, document versions, bundle version, and agreement text/version.
There is no production bundle in this change: setting the flag to true stops
startup. Only tests inject their own clearly marked document fixtures.

A visitor sees the complete notice before sign-in. A signed-in user sees the
terms, notice, and one unchecked agreement checkbox. Submission requires the
same origin, the session CSRF token, the current bundle version, and explicit
agreement. No client-supplied user, role, organization, or return URL is accepted.
The fresh WorkOS user read must match the sealed session subject and have
`emailVerified: true`. Company and personal email addresses are both eligible.
Verification means WorkOS verified the email; it does not verify age, employment,
or authority to act for a business. The approved agreement must cover the
selected adult/business conditions before the release opens signup.

Successful activation redirects to `/organizations`, which uses the existing
organization selector. It does not switch or retarget an MCP credential.
The [FS-02 change](fs-02.md) adds a portal return path to that selector and
native client guidance. Billing stays `BillingFree`:
no card, payment provider, charge, or paid subscription record is created.

## Initial grant and retained record

The reserved personal external ID is `thermus-signup:` plus a base64url SHA-256
of the WorkOS authority, a zero byte, and the subject. It contains no email.
One environment/subject can claim one personal organization under that ID.
It is not a limit of one account per human across different identities.

The organization is created with no domains and these nine metadata fields:
`schema`, `subject`, `accepted_at`, `documents_version`, `terms_version`,
`terms_sha256`, `notice_version`, `notice_sha256`, and `agreement_version`.
The schema is `thermus-signup-v1`; the server supplies the ISO timestamp.
The approved release must retain the exact versioned document and agreement
bytes. A version must never be reused for different bytes.

1. Read the retained personal organization first. If its record is valid and
   its current membership grants product access, continue. If its membership
   or grant is absent, pending, inactive, or inconsistent, require support.
2. With no personal record, existing product access continues without a new
   organization. Admin-only access does not give product access; that user may
   create a separate personal workspace. Existing roles stay unchanged.
3. Create the personal organization once, with the complete acceptance record.
   Only a successful new-create response permits the initial grant. Re-read
   the saved record and validate all effective roles before the grant. Refuse
   any existing membership in that organization, across all statuses.
4. Create one membership with the explicit `user` role. Confirm a current
   active, non-directory-managed, User-only membership and current permissions.
   Never assign Admin or Super Admin through signup.

An exception after either create permits reads only. Another process, a
repeated submission, and a restarted process can read the result, but cannot
replay the initial membership create. Unknown or incomplete results require
support. This avoids restoring a revoked membership through WorkOS
create/reactivate. The record is an initial acceptance marker, not an
acceptance history. Existing-user policy migration remains FS-03 work.

Keep this organization record after revocation. Deleting it removes the
replay barrier. A global identity suspension is separate from revoking access
to one organization. WorkOS offers no transaction across these reads and
writes: close admission and drain in-flight requests before an operator
changes an activation in progress. Switching signup off does not cancel a
write that WorkOS already accepted.

## Bounds

The existing production SDK client uses `maxRetries: 0` and a five-second
timeout. The route permits at most eight concurrent POST operations, three
attempts per subject per minute, and 1,024 retained subject counters. A full
counter table refuses new subjects until entries expire. These limits are
local to one process, not global abuse or provider-quota controls.

The form reader is bounded to 16 KiB. Membership reads use at most ten pages
of 100 records and reject a repeated cursor or malformed record. Cancellation
is checked between provider operations, especially before a write. An aborted
request keeps its admission slot until outstanding provider work settles.
Session refresh cookies survive validation failures and provider failures.
Error pages expose no provider error body or credentials.

## Provider proof on 2026-10-16

The provider contract gate ran before implementation against Thermus WorkOS
Staging with the pinned SDK 11.0.0. It used disposable organizations and made
no users, memberships, or grants. The final nine-field record proof ran three
rounds of eight simultaneous creates for one external ID in each round:

- Each round had one successful new-create response and seven refusals.
- Each refusal was HTTP 400 with code `external_id_already_used`.
- The successful response and fresh external-ID lookup had the same
  organization ID and exact metadata; the organization had no domains.
- Every new organization inherited Member with no permissions, User with
  `product:access`, Admin with `user-grants:manage`, and Super Admin with
  `admin-grants:manage` and `billing:manage`.
- A separate read of a fresh organization showed no role overrides, Member
  as the environment default, multiple roles enabled, and SSO/directory role
  assignment disabled. Every disposable organization was deleted and then
  confirmed absent. WorkOS deletion was asynchronous, so cleanup used bounded
  read polling; it did not repeat creation.

Offline SDK faults cover HTTP 500, HTTP 429, disconnect, and timeout for both
organization and membership creation: each sends one POST without an
idempotency key. Separate integration tests exercise `openWorkOSConnection`
itself and prove one attempt and a transport abort at exactly 5,000 ms.

Run the live contract through the existing Staging launcher:

```sh
pnpm exec node ~/.config/thermus/with-workos-staging.cjs npm run test:interface:workos-signup
```

The driver requires the configured Staging client and a test key. Missing
credentials fail the gate. It refuses production keys and deletes only its
own disposable organizations. The full hosted live gate remains a separate
release requirement. These results do not prove atomicity against an
out-of-band operator or a future WorkOS behavior change.
