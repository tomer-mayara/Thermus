## Acceptance specification

1. **Given** one exact release candidate, **when** its required checks finish,
   **then** each applicable command has a recorded exit status and test counts.
   Each required test passes. A skipped, cancelled, missing, or empty selection
   is not a pass. The owner reviews the complete candidate before release.
2. **Given** a checked deployment with signup off, **when** a visitor requests
   GET or HEAD `/signup`, or submits an old form, **then** GET shows the closed
   notice, HEAD has no body, POST is refused, and no activation occurs. The
   deployed revision is recorded. Existing sign-in, workspace access, portal,
   health, and protected MCP behavior still work within their contracts.
3. **Given** fresh Production configuration reads, **when** the operator checks
   organization domains, SSO and directory connections, JIT paths, default roles,
   multiple roles, and application permissions, **then** no signup or sign-in
   path gives unintended internal membership or privilege. Any unresolved
   joining path blocks opening. Keep all provider identifiers in private evidence.
4. **Given** the exact approved document bundle and operating procedures,
   **when** readiness is reviewed, **then** retained bytes, versions, hashes,
   and approval match in the restricted local store; the owner resolves remaining
   legal, transfer, and disclosure questions.
   Record existing-user evidence gaps and the separate transition decision.
   Do not infer agreement from sign-in, an invitation, or Connect consent.
5. **Given** separate publication approval, **when** matching policy and marketing
   changes are published, **then** live links reach the intended closed signup
   route and portal without JavaScript, free-access claims remain accurate, and
   published policy content matches approved source. Resolve the effective date
   explicitly. Any changed text or date needs new versions, hashes, and approval,
   with matching runtime documents. Until that approval, policies stay unchanged.
6. **Given** all prerequisites and separate authority to open signup, **when**
   the single signup setting is enabled by deployment, **then** owner-approved
   new-user checks cover a Workspace address and a personal Gmail address.
   Fresh provider verification, no initial membership, explicit agreement, and
   the current document version produce one isolated personal workspace with
   User only and the complete retained acceptance marker. No manual verification
   override, domain allowlist, internal join, privileged grant, or charge occurs.
7. **Given** a newly activated user, **when** the user reaches the portal and
   authorizes a real native MCP client, **then** the client's actual token
   workspace matches the intended personal workspace and a real page fetch
   succeeds. Browser selection does not retarget that token. Other authorized
   workspaces and existing users keep their access.
8. **Given** a retained activation and separately authorized removal checks,
   **when** signup repeats or a closed deployment is later reopened, **then**
   no old grant is replayed. Removed access stays removed after restart, other
   workspace access stays usable, and pending or uncertain activation requires
   support. Close admission and drain in-flight work before an operator changes
   access. Do not delete the retained marker as routine cleanup.

Criteria 5 through 8 describe later authorized release steps. They do not grant
permission to publish policies, enable signup, send notices, or change access.
An instruction to start FS-05 validation does not supply those approvals.
