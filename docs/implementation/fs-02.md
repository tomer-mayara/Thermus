# FS-02: portal and MCP handoff

This change follows FS-01, PR #122, which merged while this PR was prepared.
Its base is `main` with FS-01 included. Signup stays off. The change supplies
no production document bundle, publishes no policy, and changes no production
provider setting.

## Scope

- After activation, use the existing organization selector and return to the
  portal. Existing product users can continue without another agreement or grant.
- Show free access, the configured MCP address, and connection instructions.
  Browser workspace selection does not change the workspace of an MCP token.
- Give users without access a path to signup and retain invitation and support
  guidance. OAuth consent alone must never create an organization or grant.
- Preserve the retained-record barrier for pending, revoked, and uncertain
  activations. Other authorized workspaces remain usable.
- Prove new-user activation through a real Staging browser and MCP client, then
  prove the actual token workspace and isolation for a user with two workspaces.

## Behavior

Enabled signup uses a read-only inspection before it shows an agreement. With
current product access, it shows Continue. With no retained personal record or
product access, it shows the agreement. A retained record with absent, pending,
inactive, or inconsistent membership requires support. If the user has access
to another workspace, that page offers a way to select it. A failed provider
read gives an unavailable page, never an activation form.

Only POST can activate access. It retains FS-01's fresh verified-email read,
agreement, CSRF and origin checks, one-grant rule, retry barrier, and request
bounds. A successful POST and Continue lead to the existing selector with a
server-built `return_to` for the portal. Request data cannot set that path.

The protected portal response adds `plan: "free"` and the configured `mcpUrl`.
The portal displays the endpoint, free access with no card or automatic charge,
and the native client steps. Workspace links return to the portal. The text
explains that this changes only the browser; the client's verified Connect
`org_id` still selects its workspace, subject to a live grant check.

The no-organization page keeps invitation and support guidance and links to
signup availability. An authenticated MCP denial adds the same trusted signup
URL and instructions to reauthorize for the intended workspace. Neither path
creates an organization or a grant. Missing or invalid tokens still get 401;
access denial gets 403; provider failures still get 500.

Production still has no document bundle. The flag remains false by default,
and setting it true without approved documents still stops startup. The live
proof enables signup only through its test composition with TEST ONLY text.
